# 2026-10-17 日志断管道修复记录

## 问题与原因

主进程弹出 `EPIPE: broken pipe, write`，调用栈位于 `main.bundle.dev.js:55246`。对应源码是 `LR-Agent/src/main/localAgent/serverProcess.ts` 的 Python 子进程 stdout 回调：收到输出后调用 `console.log`，写到已经关闭的主进程输出管道，触发未捕获错误。

这是日志接收端断开，并不能据此判断模型调用、数据库或标注数据损坏。仅在该行添加 try/catch 不能覆盖异步 stream error，换成 stderr 也可能遇到同类断管道。

## 修复

- `src/main/logging/stdioGuard.ts`：对 stdout/stderr 分别保护，同步 write 与异步 error 中只降级 `EPIPE`、`ERR_STREAM_DESTROYED`；通道失效后丢弃后续日志并异步完成回调，不等待不可能到来的 drain。
- `src/main/logging/installStdioGuards.ts`：启动安装，`main.ts` 首行加载，早于服务和业务初始化。
- 非断管道错误继续暴露，没有添加吞掉全部异常的 uncaughtException 处理。

以上 `src/` 路径均相对 `LR-Agent/`。

## 实际验证

1. 定向 TypeScript 检查与实际主进程 webpack 构建通过，构建产物包含启动保护。
2. Jest：`src/main/logging/stdioGuard.test.ts`，1 suite / 11 tests 通过。
3. 两个真实 OS 管道用例分别关闭 stdout 和 stderr 的父进程读端。无守卫时观测到 EPIPE 并非零退出；加载实际守卫后仍观测到断管道，但独立 IPC 返回后续任务结果 5，进程正常退出 0。
4. 另覆盖同步/异步错误、正常日志、回调时序、两个通道隔离、重复安装及未知错误透传。
5. 通过已有主进程调试接口向运行实例加载同一守卫，stdout/stderr 写入后继续返回测试任务结果 5；工作窗口未销毁，加载已完成。当前窗口无需为本次修复强制关闭。

测试使用显式 `ignoreErrors: false` 的 Console 建立严格失败基线；普通 Node 全局 Console 可能自行忽略管道写失败，不能仅以其未崩溃证明修复有效。

此修复涉及运行外壳的日志可靠性，不改变 Agent、模型或标注流程。损坏的控制台通道不再接收日志；重新启动获得有效通道后恢复正常输出。
