# 读图后 network error：工具消息顺序错误复盘

日期：2026-11-11。场景：LR-Agent 本地学习与联调，默认 LangChain Agent 主线。

## 面试讲述版：一次 network error 的发现、排查、复现与修复

在这个标注 Agent 项目中，我遇到过一个问题：用户发送“分析本项目”，主代理前面列目录、读记忆、读标注都能正常执行，准备继续读图时，界面突然显示 `network error`。但用户随后明确要求调用只读子代理，子代理又能正常返回分析结果。

排查时，我先检查后端日志，发现真正导致中断的是模型服务返回的 HTTP 400，提示工具调用后没有连续收到对应的全部工具回复。本地聊天接口已经开始输出 SSE，后续模型请求发生异常，导致响应流中断，前端读取失败后显示了通用网络错误。

接着，我比较主代理和只读子代理的执行路径。当前只读子代理的工具范围不包含 `read_image_for_vision`；主代理则会在读图之后，把图片作为多模态消息交给模型。因此，我重点检查读图工具完成后的消息组装逻辑。

在视觉中间件 `VisionToolResultMiddleware` 中，我发现原实现会把“读图工具的 ToolMessage”和“图片 HumanMessage”作为同一组消息更新返回。如果同一轮还有其他工具，这条图片消息就可能夹在工具回复中间。

为了确认这个缺陷，我使用不调用真实 API 的脚本化模型，让它在同一轮发出两个工具调用，再检查下一次模型调用实际收到的消息：

① 读图工具在前、普通工具在后，得到“模型调用 A、B → A 的结果 → 图片 → B 的结果”。

② 普通工具在前、读图工具在后，得到“模型调用 A、B → A 的结果 → B 的结果 → 图片”。

③ 同一轮调用两个读图工具，第一张图片也会插在两个工具结果之间。

模型接口要求本轮 ToolMessage 连续排列，并且覆盖全部 `tool_call_id`。第一种和第三种排列不满足要求，第二种满足要求。修复前，这些组合在单独视觉中间件和业务中间件组合下共形成 6 个用例，实际出现 4 个失败、2 个通过，稳定复现了这个消息排序缺陷。

修复时，我把图片的插入时机延后：

① `_awrap()` 处理单个工具结果，先正常返回 ToolMessage。

② 需要附图时，把图片放入本次运行的 `vision_pending_images` 暂存列表。

③ 等整轮工具执行结束，在下一次请求模型前，由 `before_model()` 统一追加图片。

④ 追加后清空暂存，避免下一轮重复附图。

这样，无论同轮调用一个读图工具，还是多个读图工具，模型收到的顺序都会先包含本轮完整的工具回复，再接收图片。多个工具提交的图片通过列表合并规则汇总，清空时使用 `Overwrite([])`，保证图片不丢失、不重复。

验证时，我先确认原先失败的组合用例通过，再覆盖同轮多图、连续两轮读图、同步和异步调用，以及经过生产 SSE 适配器后的工具事件和文字输出。相关离线测试共 199 个通过，随后重启应用，确认新进程和健康接口正常。

原始失败请求体没有完整保留；日志确认了模型请求的格式错误，离线测试复现并修复了对应的消息排序缺陷。真实 DeepSeek 对话尚未复测，面试时应区分离线验证与真实 API 验证。

## 1. 用户看到的现象

用户发送“分析本项目”，主代理先列目录、读记忆和标注数据，前几步可以正常完成。准备继续读取图片时，界面显示 `network error`。

同一会话里，用户改成“调用子代理分析本项目”，两个只读子代理能返回结果。

这两个现象给出了排查方向：不是所有工具都不能用，也不是整个 Agent 服务完全不可用，需要找两条执行路径的差异。

## 2. 怎么定位到真实错误

日志里的关键异常是：

```text
openai.BadRequestError: Error code: 400
An assistant message with 'tool_calls' must be followed by tool messages
responding to each 'tool_call_id'.
(insufficient tool messages following tool_calls message)
```

这里的 `openai.BadRequestError` 是兼容接口客户端抛出的异常类型，不能因此认定请求发给了 OpenAI；本次使用的是 DeepSeek 配置。

错误链路是：

```text
客户端发起聊天请求
  → 本地服务已返回 HTTP 200，并开始输出 SSE
  → 模型发出工具调用，工具执行完成
  → Agent 组织消息，再次请求模型
  → 模型服务发现消息格式不合法，返回 HTTP 400
  → 异常从异步流中向外传播，响应流被中断
  → 客户端读取流失败，显示 network error
```

因此，外层聊天接口先返回 200，与后续模型请求返回 400 并不矛盾：它们是不同的 HTTP 请求，发生时间也不同。

日志中还出现过 MCP 会话清理的 `Session termination failed: 503`。它是另一个请求的告警；本次中断对应的致命异常是模型请求的 400，不能只看到“503”就把根因归到 MCP。

## 3. 消息为什么不合法

把工具理解成模型叫来的两位助手：A 负责读图，B 负责读标注。模型同时安排两件事后，需要先连续收齐这两件事的工具回复，再接收其他类型的消息。

这里有两个关键要求：所有 `tool_call_id` 都要有对应回复；本轮工具回复中间不能插入普通用户消息。

原实现由读图工具各自追加图片，可能形成：

```text
AIMessage：请执行工具 A 和 B
ToolMessage：A 的读取结果，tool_call_id=A
HumanMessage：图片内容                  ← 插入过早
ToolMessage：B 的读取结果，tool_call_id=B
```

图片虽然是程序自动添加的，消息类型仍然是 `HumanMessage`。模型服务处理到它时，本轮工具回复还没有连续收齐，所以拒绝整个请求。

修复后是：

```text
AIMessage：请执行工具 A 和 B
ToolMessage：A 的读取结果，tool_call_id=A
ToolMessage：B 的读取结果，tool_call_id=B
HumanMessage：图片内容
```

这里强调的是“工具回复连续且 ID 齐全”，不要求所有模型接口都必须按 A、B 的调用顺序返回工具回复。

## 4. 为什么以前不容易发现

只调用一个读图工具时，原来的顺序 `AI → Tool → Human(图)` 本身合法，所以单工具测试可以通过。

同一轮有多个工具时，是否出错与读图工具所在的位置有关：

- 先读图，再执行普通工具：图片夹在工具回复之间，会出错。
- 普通工具在前，读图工具在最后：图片排在全部工具回复后，原实现也可能通过。
- 同轮读两张图：第一张图会插在两个读图结果之间，会出错。

修复前，新增的 6 个离线组合用例实际出现 4 个失败、2 个通过，与上述规律一致。

这也解释了子代理为什么能成功：当前只读子代理的工具白名单不包含 `read_image_for_vision`，它避开了这条附图路径。子代理成功是缩小排查范围的线索，不能说明主代理的问题已经消失。

## 5. 具体怎么修复

实现文件：`LR-Agent/vendor/local-agent/app/agent/langchain_runtime/vision.py`。

`_awrap()` 负责处理一个已经完成的工具：保留其 `ToolMessage`，如果是有效的读图结果，就构造图片消息并暂存在 `vision_pending_images` 中，不立即插入 `messages`。

`before_model()` 负责下一次模型调用前的处理：此时本轮工具已经全部结束，它把暂存图片追加到消息链末尾，然后清空暂存。

`VisionToolResultState` 保存本次运行的待附图列表。它不是长期记忆，也不是整个应用共享的图片列表。

其中两个实现细节是为了保证多工具、多轮调用正确：

- 用 `Annotated[..., add]` 合并并行读图工具提交的列表，避免同时更新状态时冲突或丢图。
- 用 `Overwrite([])` 清空队列。因为队列使用列表相加作为合并规则，普通地更新为 `[]` 只是在原列表后加一个空列表，无法真正清空。

不能简单加一把锁解决：即使工具串行执行，“A 结果 → 图片 → B 结果”的消息顺序仍然不合法。需要改变附图时机，等整轮工具结束后再追加。

也不适合在 `after_model` 中读取真实工具结果：这个钩子发生在模型返回之后、工具执行之前，还拿不到本轮工具的结果。

## 6. 怎么验证

测试文件：`LR-Agent/vendor/local-agent/tests/test_langchain_runtime_stage5a.py`。

回归测试直接检查下一次模型调用实际收到的消息：对每条包含工具调用的 AIMessage，验证紧随其后的工具回复连续、数量齐全、ID 一一对应，并检查图片数量与工具实际执行次数。

验证覆盖：

- 同轮“图片工具 + 普通工具”，读图在前或在后。
- 同轮两个读图工具，验证并行更新不会丢图。
- 视觉中间件单独使用，以及与业务中间件一起使用。
- 同步调用、异步流式调用、生产 SSE 适配器。
- 连续两轮读图，确认暂存队列清空，不重复附图。
- 既有视觉兜底、工具调度、跨请求续跑和默认入口。

结果：视觉及子代理测试 47 个通过，其他相关兼容性测试 152 个通过，共 199 个通过。测试没有调用真实模型 API。

兼容性测试最初遇到终端继承的 `DEBUG=release`，不符合配置的布尔类型要求；仅在重跑相关测试的 Python 进程内临时设置 `DEBUG=false` 后通过，没有修改持久配置。

2026-11-11 已通过现有 electronmon 监视器正常重启应用；确认 Electron 主进程与本地 Agent 进程更新、窗口重新创建，新的 `/health` 返回 `ok`。这证明服务已重新启动，但健康检查不等于真实模型对话验证。

## 7. 面试追问怎么答

**这是 LangChain 自身的 bug 吗？**

本次定位到的是项目自定义视觉中间件的消息插入时机。框架允许工具通过 Command 更新状态，但项目必须保证最终消息满足模型接口要求。

**这是 MCP 协议的问题吗？**

本次缺陷发生在组织发给模型的聊天消息时。它与工具通过本地注册还是 MCP 接入是两个层次；换一种接入协议也不会自动纠正消息排序。

**为什么不增加重试？**

这是确定性的消息格式错误。把同一份不合法的消息再次发送，通常仍会返回 400，应先修正消息结构。

**为什么要测整个 Agent，不能只测中间件返回值？**

因为问题发生在多个工具结果经过框架合并之后。单独看每个工具返回的内容可能都正确，组合后的消息链才暴露问题，所以要检查下一次模型请求实际收到的完整输入。

**还有什么可以改进？**

后续可以完善流式错误呈现，让界面区分模型请求错误与普通连接异常；同时在请求模型前增加有针对性的消息完整性校验。本次已经完成的是消息排序修复与回归测试，错误展示改进尚未实施。

## 8. 表述时保留的证据边界

原日志可以确认模型服务返回了工具消息格式错误，但没有保留当时完整的模型请求体，因此不能声称已还原那一次失败的全部工具 ID 和消息内容。

代码排查与离线测试稳定复现了同类格式错误，并验证了对应修复。真实 DeepSeek API 的端到端复测尚未完成，不能说“上线后故障率归零”或“线上验证已通过”。
