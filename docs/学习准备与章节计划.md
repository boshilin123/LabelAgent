### 2.1 Agent 与 RAG 资料中重点吸收的内容

- Agent 入门：先给任务，再拆模型、消息和工具；用“模型提出调用 → 工具返回结果 → 模型继续回答”解释循环，避免一上来堆抽象类型。
- Runtime：根据是否变化、保留多久、由谁读写区分 Context、State、Store；课程中的跨调用状态要补充 checkpointer 条件，再对照项目当前的无持久化图工厂。
- Middleware：先说明业务问题，再解释模型/工具调用前后的钩子和包装调用。项目讲解必须指出具体装配顺序、门控位置及重试是否实际启用。
- MCP 与 Multi Agent：区分协议、工具和子代理。工具发现、能力过滤和同名去重先于工具调用；先掌握单 Agent，再说明只读子代理的委派和返回边界。
- RAG Agent：从模型缺少外部知识的场景出发，解释加载、切分、嵌入、检索和生成的作用。它解决知识获取问题；本项目的标注、文件操作与人工确认是执行问题，不能因为都有工具就视作同一种架构。
- RAG 查询优化：查询改写、拆解、HyDE 和路由各针对不同查询缺陷。借鉴“给原始问题 → 观察失败 → 改进策略 → 对比结果”的讲法，不把这些策略直接加进 LR-Agent。
- RAG 评估与向量库：检索质量、回答质量和基础设施选择分开讨论。对本项目则拆成协议正确性、检测质量和人工效率；课程中的某个向量库选型或效果数字不能直接套用。
- LangGraph：State、节点、边、Command、Checkpoint 和 interrupt 应围绕执行问题解释。Agent 底层运行在图上，不等于业务已经手写了 StateGraph，也不等于具备持久化恢复。

## 3. 模仿飞书的具体规范

### 3.1 章节与排版

文件命名 `LR-Agent_第NN章_主题.pdf`。正文使用“第 N 章 → N.1 → N.1.1”层级，不机械复制课程目录。每节先给可理解的业务输入，再引出概念。中文短段落，重点词少量加粗，蓝色编号标题，浅灰代码框；表格保持 3 至 4 列，流程图注明是概念示意还是实际调用链。

PDF 使用 A4 纵向、约 45 pt 页边距、约 10 pt 正文及 17 pt 行距。代码保留缩进，添加行号，单行宽度受控。必须有可点击目录、书签、页码与图表说明。复杂源码优先分段解释，不能用缩小字号代替组织内容。

### 3.1.1 后端范围与入门起点

- 不安排 Electron、React、页面、桌面 IPC 或客户端存储实现的学习任务。教材统一将其称为“外部调用方/工具执行方”，只解释后端接收什么、输出什么、如何校验和续跑。
- 正式主线是 Python → 消息与模型 → LangChain 固定链 → 工具与 Agent → Context/State → Middleware → FastAPI/SSE/续跑 → 扩展与测试 → 简历复盘。先有输入输出体验，再进入项目抽象。
- 首次出现的 `self`、类型标注、`None`、集合、继承、装饰器、异常、`async/await`、`yield` 均需解释；高级用法只在需要时展开，不要求先学完全部 Python。
- 每节控制一个主要问题。先用少量完整代码解释，再给逐行阅读指引，最后打开项目中的对应符号；不能让读者先通读数百行生产文件。
- 真实模型调用与离线固定模型明确区分。离线样例帮助理解框架执行，不证明模型理解、检测精度或实际成本。
- 每章保留“概念、实验、源码、面试”四类验收；简历表达写清个人贡献和未完成项。

### 3.2 每节的固定内容

1. 需求场景：输入是什么，当前遇到什么问题。
2. 学习目标：学完能解释、定位和验证什么。
3. 名词解析：中英文、定义、项目角色及易混概念。
4. 适用场景：什么时候用，限制是什么。
5. 实现流程：3 至 5 个主要步骤，准确标出执行方。
6. 源码阅读：真实路径、类名或函数名；行号仅作辅助。
7. 实验：完整代码、工作目录、解释器、运行命令、输出。
8. 结果解释：输入怎样转换为输出，实验没有证明什么。
9. 常见误解、回顾、练习及参考思路。

### 3.3 代码类型与证据

完整教学实验必须可独立复制运行，包含全部导入、输入和断言，不用省略号隐藏必要逻辑。源码节选注明省略范围；教学简化示例说明省掉的生产约束。现有第 1 至 9 章共 37 个完整离线实验，均从对应最终 PDF 提取后在正式环境运行通过；固定模型不会请求云服务。

分开标注“源码已确认 / 本轮已执行 / 已有验收记录 / 尚未验证”。模型精度、用户耗时、成本和吞吐量必须有单独的评价数据。通过协议测试不等于证明检测精度；两张图片成功不等于证明所有任务都稳定。

## 4. 项目事实与易混点

### 4.1 正式环境和入口

- Python：`.venvs/langchain-main/Scripts/python.exe`，3.12.0。
- LangChain 1.4.2，langchain-core 1.6.4，LangGraph 1.2.12，langchain-openai 1.2.2，langchain-mcp-adapters 0.3.0。
- 正式依赖入口：`LR-Agent/vendor/local-agent/requirements.txt`。
- `app/core/config.py::Settings.agent_engine` 默认 `candidate`，`legacy` 用于回退。保留配置值与 API 名字，不能为了教学命名美观统一改名。
- Local Agent 和 inference 分离；YOLO 依赖不混装到 Agent 环境。PowerShell 命令显式指定解释器，不依赖 IDE 自动识别。

以上 `app/` 路径均相对于 `LR-Agent/vendor/local-agent/`。

### 4.2 Agent、普通对话与工具

`app/api/v1/agent.py::local_chat_stream` 按后端设置选择入口。`app/agent/langchain_runtime/entry.py::build_engine_agent` 装配工具、业务中间件和视觉能力，`runtime.py::build_langchain_agent` 调用官方 `create_agent`。不携带工作区能力的纯聊天请求可以直接流式回答，并非每次聊天都经过完整工具循环。

`app/agent/tools/tool_registry_meta.py` 的 `ToolRunner` 是业务执行分类：SYNC 是本轮后端执行；PROPOSAL 是后端校验并生成提案、客户端确认落盘；ASYNC 是交给 Electron 执行后回传续跑。不能把它们直接等同 Python 的同步函数与 `async def`。

### 4.3 Context、State、Memory 与 Checkpoint

- `AgentContext`：单次调用注入的模式、工作区、客户端工具名和已完成工具 ID。语义上保持静态，Pydantic 模型没有配置 `frozen=True`。
- `BusinessRoundState`：Agent 图执行中的业务回合字段，不能自行等同跨请求持久状态。
- `app/agent/langchain_runtime/resume.py`：基于客户端请求中的消息、结果和上下文重建续跑；不是服务端持久化图恢复。
- `LR-Agent/src/main/checkpoint/turnCheckpointStore.ts`：文件/标注前后业务快照，用于撤销；不是 LangGraph checkpointer。
- 当前 `build_langchain_agent` 未传 checkpointer 或 Store。课程中的跨请求图恢复、`interrupt`、长期 Store 示例不能直接写成项目现有能力。
- SQLite、Markdown Memory 和认证后端 PostgreSQL 各有业务用途，不自动等于 LangGraph Store，更不是向量知识库。

### 4.4 阶段门控与能力边界

`app/agent/assist/task_phase.py::derive_task_phase` 根据结构化提案状态推导阶段；主要门控是待确认时阻止写入、确认后阻止对已处理路径重复标注。SCAN/ANNOTATE/REPORT 目前是语义标记，不是强制线性 StateGraph。

`explore_readonly` 是只读子代理工具，不代表项目存在完整的 Planner/Executor/Reviewer 系统。MCP 用于发现和适配工具，不是 RAG。当前重试件的工具重试白名单为空，不能笼统宣称全部工具自动重试。

RAG 资料可以帮助讲解知识缺口、分块、查询优化和评估方法，但本项目重点是工作区工具、标注和人工确认。课程中向量库的取舍不能直接变成本项目需求。
