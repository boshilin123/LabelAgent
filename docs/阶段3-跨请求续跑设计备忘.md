## 1. 结论：选方案 A（保持跨请求 `client_tool_results`，不引入 checkpointer）

- **方案 B（框架 `interrupt()` + 持久化 checkpointer）的成本**：`langgraph/types.py:946` 官方明写「A checkpointer must be enabled for interrupts to work!」；`Command(resume=)` 会重放被中断的节点（`types.py:1006-1019` 只做去重、不能阻止重放；`experiments/VERIFICATION-2026-09-23.md:33-35` 实测**副作用执行两遍**）。选 B 必须同时完成：持久化选型 / 线程 id / 清理策略（计划 §3 已排除）、中断前零副作用重构、幂等键、重复恢复处理——等于重设计持久化。
- **方案 A（本推荐）的成本**：没有框架中断能力，回合终止靠 §2 的两段式；"会话"只存在于请求体，服务端无状态。
- **A 做不到的事**：跨请求的服务器端状态、不依赖前端重发消息的断点续跑、HTTP 轮内恢复。注意：`docs/阶段4-SSE适配设计备忘.md:25` 记载的 `updates["__interrupt__"]` 分片在方案 A 下**永不出现**，阶段 4 必须改走 `custom` 帧。

## 2. 回合终止：两段式（已用实际安装包探针验证）

**不可用的做法**：在 `after_model` 里 `jump_to="end"`——会跳过 tools 节点（见文首复核 1）。

**可用做法**：

1. `after_model`（`@hook_config(can_jump_to=["end"])`）读 `state["messages"][-1].tool_calls` 算出本轮计划，用 `runtime.stream_writer(round_plan_frame)` 发「本轮计划」帧；把 **ASYNC / 被合并 / 被门禁** 的调用写成**合成 `ToolMessage`** 注入（`factory.py:1953-1957` 据此把它们从 `pending_tool_calls` 剔除，永不进 ToolNode，与官方 `ToolCallLimitMiddleware` 同法）。
2. **SYNC 调用照常进入 tools 节点执行**（帧序与基线一致）。
3. `before_model` 断路器：当「存在已挂起且本轮已补齐的 ASYNC id」→ `return {"jump_to": "end"}`（`factory.py:1775-1784` 允许 `before_model` 跳转）。

**P3 探针实测输出**（migration 环境、脚本化模型、无网络）：

```
before_model → model → CUSTOM pending → after_model[ToolMessage c1] → tools[ToolMessage s1] → CUSTOM turn_end → before_model
```

**模型调用 1 次、SYNC 执行 1 次、零第二次模型调用。**

**SSE 字节一致的要点**：
- 合成 `ToolMessage` 与空的 `*.before_model` / `*.after_model` updates **不得产帧**；
- `done` 仍只由 `app/api/v1/agent.py:498` 发出（阶段 0 §8-7）；
- ASYNC 工具的 `tool_start` 载荷与 `pending_emitter.py:22-28` 同构（`json.dumps(args, ensure_ascii=False, indent=2)`），`tool_pending` 走 `to_sse_dict()` 的双写 `clientToolCalls` + `toolCalls`。

**与阶段 1 的冲突（必须改）**：`runtime.py:273-283` 的 messages 流早停要被上述 middleware 终止取代（`client_tool_names` 保留为结构防线，不再作为终止判据）。

## 3. Resume 机制（方案 A）

复用 `app/agent/context_service.py:73-117` 的 `append_client_tool_results_to_messages`：

1. `unanswered_tool_call_ids()`（`:37-48`）只对**真正缺失**的 id 追加 `ToolMessage`（客户端重发的 pending `AIMessage` 已声明该 id）。
2. `enrich_resume_tool_result()`（`:51-70`）必须在**模型看到之前**改写：VERIFY 阶段且 `proposal_pending is True` → 改为 `proposal_pending=false / file_written=true` + `RESUME_APPLIED_NEXT_HINT`；否则补 `RESUME_NEXT_HINT`。这就是"谎报防护"。
3. 从未回来的 id 保持没有 `ToolMessage`（与旧路径同态：`emit_tool_pending` 不补 `ToolMessage`）。

**另需播种**：`assist_service.py:84-85` 的 `completed_ids` → 新增 `AgentContext` 字段 → `after_model` 把已答 id 从本轮计划中剔除（替代 `tool_loop.py:458-461` 的 `completed_tools` 过滤）。

## 4. 幂等 / 无双重副作用

方案 A 下唯一的副作用是后端 SYNC 写入与标注写盘，而**标注写盘只由客户端执行**（阶段 0 基线 `TestMultipleTools::test_sync_and_async_tool_same_round_executes_sync_then_pends` 钉住 ASYNC 后端零执行）。resume 请求内不存在服务端副作用代码路径 → **不可能写两次**。

重复投递的 resume 同样安全：第 2 条按 state 内 `ToolMessage` 的 id 过滤，重复 id 被跳过；`client_tool_results` 是请求体数据、不是持久状态。

**必须活在请求外的状态：无。** 唯一例外是旧路径既有的 `app/api/v1/agent.py:49` 的 `_cancel_events` 注册表。

- **实测**：`after_model` 里 `jump_to="end"` 与自定义帧都生效；`stream_mode` 需要加入 `"custom"`（`runtime.py:48` 的 `STREAM_MODES`）。

- **阶段 2/3 边界**：被 coalesced/blocked 的调用，其 `tool_start`/`tool_result` 由适配器按「本轮计划」帧发出，**middleware 不得直发 SSE**。
